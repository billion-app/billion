# Election process prototype (#419)

This hand-authored, source-linked education route teaches nomination versus election using three explicitly labeled examples. It is independent of ballot-provider access and candidate analysis. The single Elections invitation links to `/election-process`; #418 can preserve that hook when replacing the entry screen.

It deliberately has no candidate roster, current contest stage or scheduled milestone. A production contextual flow requires a dated authority record identifying office, district/jurisdiction, election year and kind, verified stage, next official milestone, applicable party rules and source URL. Unknown values must remain unknown. Registration and party affiliation cannot be inferred from an address. The #396 watchlist remains research-only; filing and declaration cannot establish ballot access or nomination.

Before publishing, editorial review must check summaries and authoritative links, especially special-election exceptions and Texas runoff rules. First-time voters must use each example and explain nomination versus election, describe the selected system and find their own next official action. Record comprehension failures and iterate; automated review does not satisfy this gate. Native production runtime, Dynamic Type and screen-reader verification remain required before declaring #419 complete.

The UI’s dated source-consultation line is not a freshness guarantee. A subsequent content edit must recheck the sources and update that line. No scraped text, AI generation, provider writes or registration assertions are involved.

## Rigorous design revision

The original captures above are historical implementation evidence. The finished redesign is in `design-revision/`: initial presidential/California/Texas examples, the integrated Elections entry, expanded participation and sources, and enlarged web text. All are actual running Expo web development screens at 390 × 844 with hand-authored educational content. The text stress capture multiplies browser text sizes and line heights by 1.5; it does not exercise React Native font-scale behavior or certify native Dynamic Type. The compact “no live updates” label is the truthful sparse state: these static examples do not request or invent current contest status. There is no new data-request error state; official-link opening failures retain the shared `SourceLink` retry behavior.

A fresh Astra reviewer first viewed the original screenshots without implementation rationale. In three substantive iterations we moved the explanation above eligibility, grouped the stages into one connected surface, used comparable example tabs, replaced repetitive caveats with participation/source disclosures, visually separated Texas’s conditional runoff, shortened and clarified the presidential journey, connected the reader’s vote to delegates and electors, and made the election-office handoff label honest. Switching examples resets scroll and disclosures so the scope line remains visible. The independent root four-PR audit’s #435 findings were addressed in the same revision.

The same reviewer’s final assessment: “I’m now impressed by all three as polished, approachable explainers for an unfamiliar voter.” Its reasons were specific: California explains same-party advancement; Texas makes the runoff conditional; President connects voters to delegates and electors; explanation comes before caveats, with deeper detail optional. The reviewer recommended no further meaningful design change. Editorial signoff, novice comprehension tests, native accessibility and live contextual status remain separate open gates.

For this revision, Expo typecheck, focused ESLint/Prettier, Expo tests (184 passed, one skipped), and production iOS export passed. The prior workspace scraper subprocess timeouts remain documented above; no scraper changes were made.
